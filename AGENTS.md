# Правила для ИИ-агентов (System Rules)

При работе над этим проектом ты **обязан** соблюдать следующие правила:

## 1. Соглашение об именовании коммитов (Conventional Commits)
При создании любого коммита строго соблюдай спецификацию:
- **Формат:** `<тип>[необязательная область]: <описание>` (после двоеточия обязателен пробел).
- **Регистр:** Типы пишутся строго в нижнем регистре (`feat`, `fix`, `docs`, `chore` и т.д.).
- **Время и наклонение:** Используй Present Tense и Imperative Mood (повелительное наклонение). 
  - ✅ *Правильно:* `add feature`, `move cursor`, `fix bug`.
  - ❌ *Неправильно:* `added feature`, `moves cursor`, `fixed bug`.
- **Допустимые типы:**
  - `feat`: Новая функциональность.
  - `fix`: Исправление ошибки.
  - `refactor`: Изменение кода без изменения поведения.
  - `docs`: Работа с документацией/README.
  - `style`: Изменение стиля/форматирования кода.
  - `test`: Добавление или исправление тестов.
  - `perf`: Улучшение производительности.
  - `build`: Изменения в системе сборки и зависимостях.
  - `ci`: Изменения в конфигурации CI.
  - `chore`: Вспомогательные изменения (не затрагивают код и тесты).
  - `revert`: Откат ранее сделанного коммита.
- **Запрещено:** Использовать тип `init` и прошедшее время.
- **Пример:** `feat(backend): implement docx reader service`

## 2. Обновление документации (README.md)
После успешного завершения **любой** задачи или этапа, перед тем как отчитаться пользователю, ты **обязан обновить файл `README.md`** в корне проекта.
- Найди или создай раздел **«Прогресс разработки»**.
- Отрази текущий статус этапа (например: "Этап 2: Реестр шаблонов и Regex-экстрактор — ЗАВЕРШЕН").
- Кратко опиши, какие новые классы, эндпоинты или таблицы БД были добавлены.
- Если были изменены команды запуска или добавлены новые зависимости, обнови соответствующие разделы инструкции.
- **Никогда не завершай задачу, пока не обновишь `README.md`!**

## 3. Стандарт комментирования кода (Code Commenting)
Ты обязан документировать код. Комментарии должны объяснять **ПОЧЕМУ** (Why) и **БИЗНЕС-ЛОГИКУ** (Business Logic), а не **ЧТО** (What) делает код.

**Правила для Java (Backend):**
- Для всех публичных классов и методов (Service, Controller, Repository) используй **Javadoc** (`/** ... */`).
- В Javadoc обязательно указывай: назначение метода, входные параметры (`@param`), возвращаемый результат (`@return`) и исключения (`@throws`).
- Внутри сложных методов (например, регулярные выражения или логика сравнения) используй строчные комментарии (`//`), чтобы объяснить неочевидные решения.

**Правила для React/TypeScript (Frontend):**
- Для всех React-компонентов и сложных функций используй **JSDoc** (`/** ... */`).
- Описывай пропсы (`props`) и состояние (`state`).
- Для хуков `useEffect` обязательно пиши комментарий, объясняющий, почему этот эффект вызывается и от каких зависимостей он зависит.

**Запрещено:**
- Писать комментарии вида `// Увеличиваем i на 1` (это очевидно).
- Оставлять закомментированный («мертвый») код.

## 5. Стандарт сквозных заголовков (Headers)
При разработке любых REST-контроллеров и вызовов внешних/внутренних сервисов ты обязан следовать корпоративному стандарту заголовков (Раздел 2. Требования к заголовкам):

**Обязательные заголовки от UI/Внешних систем:**
- `Operation-Id` (Transitive) — идентификатор операции (например, "GET_REPORTS").
- `x-call-id` (Transitive) — сквозной UUID запроса (UUID v7). Если отсутствует — генерировать новый.
- `x-mdm-id` (Transitive) — идентификатор клиента (опционально, если есть).
- `x-user-session-id` (Transitive) — ID сессии (опционально, если есть).
- `X-Segment-Key` (Transitive) — ключ маршрутизации (номер заявки, опционально).

**Обработка:**
- Все Transitive заголовки должны быть доступны в контексте запроса (через ThreadLocal или RequestContextHolder), чтобы их можно было записать в логи и передать дальше.
- Если заголовок отсутствует, но он не обязателен (например, `x-mdm-id`), сервис не должен отклонять запрос (обработать с доступными данными).
- Никогда не логировать `Authorization`, `Cookie`, `device-fingerprint` в открытом виде.

**Swagger:**
- В Swagger UI все эти заголовки должны быть описаны через `@Parameter(in = ParameterIn.HEADER, description = "...")`.

**Запрещено:** Использовать устаревший заголовок Client Session Header (заменен на `x-user-session-id`).
